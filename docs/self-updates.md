# Application self-updates

8BitDo Updater uses [tufup](https://github.com/dennisvang/tufup) and [The Update Framework](https://theupdateframework.io/) to verify application updates against a public trust root bundled with the application. Application updates and controller firmware updates are separate operations. Updating the application never authorizes a firmware write.

## Update an installed application

The desktop settings panel checks either the **Stable** or **Alpha** channel. Alpha includes prereleases and stable releases. Neither channel permits a downgrade. Read the available version and release notes before confirming installation.

From a standalone binary, run:

```sh
eightbitdo app-update-check --channel stable
eightbitdo app-update-apply VERSION --channel stable --confirm
```

Replace `VERSION` with the exact `available_version` returned by the check. Use `--channel alpha` in both commands to include prereleases. The backend checks the signed metadata again and rejects a different version from the one you reviewed.

Run application self-updates with the default state directory. A CLI invocation using a different `--state-dir` reports self-updates as unsupported. Firmware jobs using custom state directories still participate in the shared application-update guard.

Self-updates support the standalone executable, the Linux desktop AppImage, the complete macOS `.app`, and the Windows desktop installation directory. The application directory must be writable. A desktop update replaces the frontend and its bundled backend together. Source checkouts, Python package installations, and Decky report that self-updates are unsupported; update those through their original installation method.

Windows updates preserve the existing `uninstall.exe` generated by [Tauri's NSIS installer](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi). Portable installations do not need that file. Self-updates do not change installer registry metadata; Windows may show the originally installed version in its installed-apps list until you run a newer installer.

Desktop updates download and stage the verified application, then return `state: "staged"`. Quit the application to finish installation, then reopen it. The installer waits for both the desktop process and its backend to exit. Windows standalone updates likewise finish after the CLI exits. On Linux and macOS, standalone CLI updates replace the executable before returning `state: "installed"`.

A staged result is not a completed installation. The detached installer waits up to five minutes for the application to close. If it is interrupted or times out, the pending transaction continues to block firmware jobs until you recover it. The installer does not request administrator access, purge an installation directory, or automatically restart an application that might still be updating.

## Recover an interrupted application update

The installer keeps the previous application as a sibling named `.NAME.8bitdo-backup-TOKEN`. If replacement fails after moving the original application, it attempts to restore that backup. A durable transaction marker prevents new firmware jobs while replacement or recovery is unresolved.

If the application still opens, close other instances and use the desktop recovery action or run:

```sh
eightbitdo app-update-recover --confirm
```

This rolls back a pending application transaction, removes only its staging files, and clears the firmware-job block. If desktop or Windows recovery needs to replace the application, it stages a detached rollback and asks you to quit first. Reopen the application after rollback completes. The command refuses a transaction belonging to another installation or an installer that is still running. It does not revert a completed update.

If an interruption left the application path missing, restore its sibling backup to the original name while all application processes are closed, then open the restored application and recover the pending transaction. Keep the backup until the new version works. The updater retains backups and copied installer helpers under its own state directory; it does not delete unrelated files to reclaim space.

## Frontend API

These operations use the existing versioned JSON envelope:

| Operation | Parameters | Result |
| --- | --- | --- |
| `check_app_update` | `channel`: `stable` or `alpha` | Current and available versions, signed release notes, platform, architecture, and whether installation is available. |
| `apply_app_update` | `channel`, exact reviewed `version`, `confirmed: true` | `installed` for synchronous replacement, or `staged` while waiting for the application to exit. |
| `recover_app_update` | `confirmed: true` | `recovered` after rolling back an interrupted transaction. |

Check results include `current_version`, `channel`, `platform`, `arch`, `available_version`, `release_notes`, `state`, `can_apply`, `can_recover`, `restart_required`, and `message`. Check states are `unsupported`, `current`, `available`, `staged`, and `interrupted`. A staged update becomes interrupted if its installer process exits without clearing the transaction; only then does `can_recover` become true. A failed signature, expired metadata, unavailable repository, wrong application/platform/architecture, busy firmware worker, or changed reviewed version produces an API error, never an “up to date” result.

Downloads and verification run during the apply request. Frontends should display an indeterminate progress indicator while waiting and use the returned state afterward. They must not report installation complete from a staged result. No frontend can supply an installation path or an update server through this API.

Firmware-job submission and application replacement share an interprocess lock. Application updates reject queued or active firmware jobs and still-running firmware workers. Queuing firmware work rejects a pending application transaction. The detached installer uses the same lock during replacement.

## Repository and trust layout

Each application/platform/architecture has an independent metadata history, for example `eightbitdo-desktop-macos-aarch64` or `eightbitdo-cli-linux-x86_64`. All repositories can share the same initial root and signing roles. The full repository name and signed target metadata bind each payload to its application, OS, architecture, and version.

The bundled `eightbitdo/resources/update-config.json` contains:

```json
{
  "metadata_base_url": "https://raw.githubusercontent.com/trevor-scheer/8bitdo-deck/updates/",
  "target_base_url": "https://github.com/trevor-scheer/8bitdo-deck/releases/download/",
  "release_targets": true
}
```

Clients fetch metadata from `METADATA_BASE/APP_NAME/metadata/`. The signed target's `release_tag` selects `TARGET_BASE/RELEASE_TAG/ARCHIVE_NAME`. TUF verifies the target length and hashes before extraction. Metadata and trusted-root rotation state are cached separately for each repository. The bundled `tuf-root.json` is only the initial trust anchor; an existing client's trusted root is not reset from the bundle.

Archives contain exactly `application` and `update-manifest.json`. The application is one executable, AppImage, complete `.app`, or Windows app directory. The manifest repeats the signed platform/product/version identity. Before extracting, the client rejects unrelated archive paths, traversal paths, special files, and links outside the application. The installer copies the verified application to a sibling staging path, saves the original as a backup, and moves the staged application into place. It never merges arbitrary archive contents into the parent directory.

## Bootstrap signing keys

Use the project's locked Python environment, which includes tufup. Keep signing keys outside the Git checkout. The following commands create one initial repository and four Ed25519 role key pairs:

```sh
uv run python scripts/tuf_repo.py init \
  --repository PRIVATE_DIR/repositories/eightbitdo-cli-linux-x86_64 \
  --keys PRIVATE_DIR/keys \
  --app-name eightbitdo-cli-linux-x86_64
```

Replace `PRIVATE_DIR` with a private, backed-up directory. The utility creates the key directory with private permissions and refuses to generate replacement keys over an incomplete key set. Each role has a private file (`root`, `targets`, `snapshot`, or `timestamp`) and a corresponding `.pub` file. Never commit private files or put them in release assets.

Keep the private `root` key offline. CI needs only the private `targets`, `snapshot`, and `timestamp` keys, plus all four public `.pub` files. Store the online private keys in repository secrets and materialize them in a temporary restricted directory for signing. The initial signed `metadata/root.json` is public and belongs in the application bundle as `tuf-root.json`.

To initialize another repository with the same root, add `--root`:

```sh
uv run python scripts/tuf_repo.py init \
  --repository UPDATE_CHECKOUT/eightbitdo-desktop-macos-aarch64 \
  --keys ONLINE_KEYS_DIR \
  --app-name eightbitdo-desktop-macos-aarch64 \
  --root eightbitdo/resources/tuf-root.json
```

`UPDATE_CHECKOUT` holds the persistent `updates` branch. `ONLINE_KEYS_DIR` holds the public keys and online private keys described above. Reuse existing metadata for every release; do not recreate repositories or reset their version counters.

## Publish a release

Build and test the complete application unit first. Then add it to its repository:

```sh
uv run python scripts/tuf_repo.py add \
  --repository UPDATE_CHECKOUT/eightbitdo-cli-linux-x86_64 \
  --keys ONLINE_KEYS_DIR \
  --app-name eightbitdo-cli-linux-x86_64 \
  --bundle out/eightbitdo \
  --version 0.3.0a1 \
  --release-tag v0.3.0-alpha.1 \
  --notes-file RELEASE_NOTES.md
```

`--bundle` names the actual executable or complete desktop application unit, not its installer or outer release archive. The utility creates the application-only archive in that repository's `targets` directory and prints its path. It uses tufup's repository implementation to sign and version the target, snapshot, and timestamp metadata, then verifies every role's signatures. It refuses an existing or older release version.

Upload the generated archive to the matching immutable GitHub Release before publishing the updated metadata. Commit the repository's `metadata` directory to the `updates` branch. Keep every numbered root file so older clients can follow root rotations. Do not commit the key directory or `.tufup-repo-config`, which contains local build paths. Preserve metadata history across releases and serialize publishing jobs so competing releases cannot overwrite it.

## Refresh metadata and rotate keys

Metadata expires even when no release is published. Run a daily workflow for every repository:

```sh
uv run python scripts/tuf_repo.py refresh \
  --repository UPDATE_CHECKOUT/eightbitdo-cli-linux-x86_64 \
  --keys ONLINE_KEYS_DIR \
  --app-name eightbitdo-cli-linux-x86_64
```

The utility refreshes and signs the online roles without the private root key. Timestamp metadata lasts two days, snapshot metadata seven days, and targets metadata 30 days. Publish the refreshed metadata and monitor scheduled workflow failures. Expired metadata causes clients to refuse update checks; the application and firmware features remain usable.

The root expires after 365 days. Before expiry, use tufup's [repository key-management API](https://tufup.readthedocs.io/en/latest/api.html) in the offline signing environment to refresh or rotate it. Root rotation must retain the old-to-new signature chain and publish each numbered root version. Review the resulting public root, distribute it through every repository, and include the newest root in subsequent builds. Do not rotate roots by regenerating keys or replacing the bundled JSON alone.

## Validation

`tests/test_selfupdate.py` creates real signed repositories and serves them over a local HTTP server. It verifies stable/alpha selection, no-update results, confirmed application replacement, unchanged neighboring files, retained backups, tampered metadata and target rejection, platform binding, archive path restrictions, firmware-job exclusion, detached-installer waiting, interrupted rollback, and refresh without the private root key. These tests update temporary fixture files and never access controllers.
